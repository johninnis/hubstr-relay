# 42. NIP-17 is advertised while the guest policy accepts gift wraps addressed to a tenant

## Status

Accepted

Supersedes ADR-0033. Carried forward unchanged: whether 17 is in `supported_nips` follows the live guest policy, read on every request through one predicate, `GuestPolicy::servesAsDirectMessageInbox()`, and the other NIPs stay a static list in the configuration. Revised: what the predicate asks. A gift-wrap kind in `read.kinds` or `read.global_kinds` no longer withdraws 17, and the predicate holds whenever the guest write policy admits a wrap addressed to a tenant, by whichever provenance route it offers, where ADR-0033 asked for `tagged_to_tenant` alone. This record holds the complete current decision.

## Context

*Carried forward from ADR-0033.* NIP-17 describes how a relay serves as a direct-message inbox. It accepts kind 1059 gift wraps addressed to its users, and "Relays SHOULD protect message metadata by only serving `kind:1059` events to users p-tagged on the event (enforced using NIP-42 AUTH)". A sender's client reads the recipient's kind 10050 list to choose where to deliver, and NIP-11 defines `supported_nips` as "a list of NIP numbers supported by the relay", so a client can check that a listed relay takes the message.

Whether this relay takes a wrap is runtime configuration. `setguestpolicy` can remove 1059 from the writable kinds or change the provenance checks a guest event must meet, and after either a wrap addressed to a tenant may be refused. The `supported_nips` list, though, is assembled once from the config file. A static 17 would be true on the day the relay started and a lie the moment an operator changed the policy, and a lie in that field sends direct messages to a relay that will refuse them. The relay-information document is already built on every request: the name, description and icon overrides are read from the live policy projection each time ([ADR-0006](0006-policystate-is-a-mutable-in-process-read-model.md)). The supported list can be read the same way.

*What this record adds.* ADR-0033 also withdrew 17 while 1059 was in the readable or global kinds, because the guest policy alone decided who could read a wrap, and a guest-readable wrap was served to anyone who asked. That is no longer so. innis/nostr-relay hands the store the keys a connection authenticated as, after whatever the host's policy answers, and on every filter the store matches a kind 1059 or 21059 event only where its `p` tag names one of them (nostr-relay ADR-0036, this store's condition in [ADR-0043](0043-the-gift-wrap-rule-is-a-membership-test-in-each-filters-query-and-in-the-delete.md)). Only a tenant can authenticate here ([ADR-0004](0004-nip42-is-a-tenant-only-scope-lift-offer-not-a-connection-gate.md)), so a guest reads no gift wrap whatever the guest policy grants, and a tenant reads only the wraps addressed to it. The serving half of NIP-17 is the library's and holds under every policy; only the accepting half depends on this relay's configuration. Withdrawing 17 for a readable kind told senders that the relay would expose their mail when it would not, and sent their messages elsewhere for nothing.

ADR-0033 also read the accepting half as `tagged_to_tenant` alone, and that was never what admission does. The guest provenance checks are alternatives ([ADR-0019](0019-guest-write-provenance-is-a-set-of-alternatives.md)): `tagged_to_tenant` admits an event of any writable kind whose `p` tag names a tenant, a tag prefix rule ([ADR-0044](0044-a-tag-prefix-rule-admits-only-the-kinds-it-lists.md)) admits an event of one of its kinds carrying its tag with a value that starts with one of its prefixes, and a policy configuring neither admits every event of a writable kind. A NIP-17 wrap carries one `p` tag naming its recipient. So a relay with `tagged_to_tenant` off took every wrap when no rule was configured, and took a wrap to a tenant when a rule on the `p` tag covering kind 1059 matched that tenant's key, while not advertising 17 in either case. Reading the condition from a second statement of the admission rules is how it drifted from them.

## Decision

`GuestPolicy::servesAsDirectMessageInbox(PublicKeyCollection $tenants)` holds when, for at least one tenant, the write policy admits a wrap of kind 1059 whose tags are a single `p` tag naming that tenant. It asks `GuestWritePolicy::admissionFailure`, the one method `HubstrPolicy::allowEventSubmission` asks of every guest event, which checks the kind gate and then the provenance alternatives; the predicate repeats neither, so it and admission cannot disagree. `Nip11InfoProvider` passes the current tenants and appends 17 to the configured supported list only while the predicate holds, so the document says 17 exactly when a wrap a sender addresses to a tenant is accepted. The read kinds and global kinds do not enter the predicate.

A rule on the `p` tag counts only when its kinds include 1059. A wrap carrying an extra tag only matters if a rule scoped to 1059 checks that tag, so NIP-17 is not advertised where only such a rule would admit it: a sender following NIP-17 and NIP-59 adds no such tag.

The other advertised NIPs stay a static list in the configuration, because nothing at runtime changes whether the relay implements them.

## Consequences

- A sender's client sees 17 on this relay exactly when a wrap it sends to a tenant will be accepted, and every wrap the relay accepts is served only to the keys it names. Removing 1059 from the writable kinds, or leaving only provenance checks that a wrap's `p` tag cannot meet, removes the advertisement in the same request.
- A relay with `tagged_to_tenant` off and no tag prefix rule advertises 17, because it admits every wrap. A relay whose only rules check page tags does not, whatever kinds they list, and neither does one whose `p`-tag rule lists only other kinds.
- A gift-wrap kind added to `read.kinds` or `read.global_kinds` leaves 17 advertised. It still undoes the policy gates of [ADR-0036](0036-both-gift-wrap-kinds-are-guest-writable-and-excluded-from-the-guest-readable-kinds.md), which keeps prohibiting it for `global_kinds`; it no longer exposes a wrap, so it no longer changes what the relay tells senders.
- Do not add the read clause back as defence in depth. The confinement that makes it unnecessary is the library's and binds every policy; a read clause here would only withdraw 17 from a relay that still serves NIP-17 correctly.
- Do not restate the kind gate or the provenance rules in the predicate. It asks the same `admissionFailure` admission asks; a second statement is what let ADR-0033's condition miss two of the three routes.
- The predicate is the one definition of "this relay is an inbox". Do not add a config key or a second flag for it; the guest policy and the tenant set already carry every fact it needs, and a separate switch could disagree with them.
- Do not make 17 static "because it is the default". The default is the common case, not the only one, and the field is read by clients deciding where to send private mail.
- Do not move the other NIPs into the same per-request computation for uniformity. They do not vary, and reading them from the live policy would suggest that they might.
- `GuestPolicyTest` pins each route: a guest-readable or global gift-wrap kind, a `p`-tag rule listing 1059 whose prefix a tenant's key meets, no provenance check and `tagged_to_tenant` all leave 17 advertised; a non-writable 1059, a page-tag rule alone, a page-tag rule scoped to 1059, a `p`-tag rule no tenant's key meets, a `p`-tag rule listing only other kinds and a relay with no tenant withdraw it. `Nip11InfoProviderTest` pins the advertisement itself, and `HubstrPolicyTest` pins that admission takes a wrap to a tenant by a `p`-tag rule and with no provenance check.
- Shared decision: nostr-adrs ADR-0122.
