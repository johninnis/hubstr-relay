# 34. The event store holds only the relay's own encoding of an event and files it under its nostr-core address

## Status

Accepted

## Context

nostr-relay streams stored events as the bytes the store holds, without parsing or re-encoding them (nostr-relay ADR-0021). That is safe only because of where the bytes came from: a signature covers an event's fields, not the JSON it arrived as, so the relay may send unparsed bytes only for an event it verified. nostr-relay states that as an obligation on the store; this relay's store is where the obligation is met or broken.

The events table has one column holding an event's bytes, `raw_event`, and one statement writing it, in `EventWriteStore`. Both write paths reach that statement with an `Event`: the running relay through the write worker, and `bin/import.php` directly (ADR-0008). Neither hands the store a string. So for every row written from now on, the bytes are what `EncodedEvent::of()` produced from an event that passed validation.

Rows already on disk are a different matter. Before nostr-core stopped keeping an event's input bytes (nostr-core ADR-0076), `Event::toJson()` returned the string an event had been parsed from. Events arriving over a WebSocket were stored in the relay's own encoding anyway, because the message parser re-encoded them, but the import tool parsed each line with `Event::tryFromJson` and stored the line itself. A relay that has imported anything therefore holds rows whose bytes are whatever the export it imported from contained: another key order, whitespace, or keys no signature covers.

Rewriting those bytes canonically cannot be done in SQL: SQLite's JSON functions could rebuild an object from its known keys, but not with the byte-for-byte encoding the relay uses, and not with PHP's reading of an input that repeats a key, which is the reading the event was verified under. It would take a PHP pass over every row — and such a pass was built: chunked, resumable across restarts through a marker table, and proven lossless against a corpus of over a thousand events authored by other clients, every one of which still verified against its signature after re-encoding. It was then cut before release. The deployment is a single operator's cache relay: every old row already passed `EventValidator` at admission (id hash and signature over the signed fields), the subscription read path has always streamed `raw_event` unparsed (ADR-0003), so those bytes have been served exactly as they are since they were written, and nostr's model has the client verify events rather than trust a relay's bytes. A re-encoding pass changed nothing any verifier sees; its cost in machinery was real and its benefit hygiene. An operator who wants a fully canonical store gets one by exporting with the old binary and re-importing, because import re-encodes through admission.

The address half of the problem is not hygiene. Replacement of a replaceable or addressable event and NIP-09 deletion by coordinate both have to find the stored event at an address: its pubkey, its kind and its identifier. The store used to work that identifier out for itself, from the first `d` tag in the tags table, while nostr-core's `EventCoordinate::tryFromEvent()` is the definition every other part of the ecosystem uses, reading the `d` tags as one claim (nostr-adrs ADR-0014, nostr-core ADR-0092): the value when they agree, no address at all when they disagree, the empty identifier when none carries a value, and the empty identifier for every replaceable kind whatever its tags. Two definitions of an event's address can disagree, and where they disagree the relay replaces or deletes a different event from the one a client named. Working the identifier out for rows already stored means reading each row's tags — which, unlike canonicalising bytes, SQL's JSON functions can do exactly, because extraction is all the column needs.

## Decision

`raw_event` holds only `EncodedEvent::of($event)`, and `address_identifier` holds only `EventCoordinate::tryFromEvent($event)?->getIdentifier()`: an identifier, possibly empty, for a replaceable or addressable event and `NULL` for any other. The one statement that writes them is the insert in `EventWriteStore`, for an event the relay was handed through `EventWriterInterface::store()`. Nothing may insert into `events` except through `store()`. Replacement and deletion by coordinate match `pubkey`, `kind` and `address_identifier`, and no longer read the `d` tag from the tags table.

Rows written before these rules keep their `raw_event` bytes and have their address backfilled, both inside migration 0002. The migration adds the column, sets the empty identifier on every replaceable-kind row, and sets every addressable-kind row's identifier from its `d` tags with SQLite's JSON functions, replicating the library's reading exactly: no `d` tag carrying a value is the empty identifier, values that agree are that value, values that disagree leave the column `NULL`. The index over `(pubkey, kind, address_identifier)` is created in the same migration, so the whole change lands in the one transaction `SchemaMigrator` wraps every migration in, tracked by `PRAGMA user_version`: no marker table, no chunking, no resume logic, and an interrupted start rolls the migration back whole.

`EventQueryStore` reads the bytes back through `EncodedEvent::fromOwnStore()`, the one place it does so. For rows written from now on the provenance that call trusts is the relay's own encoding; for rows from before, it is an event verified at admission whose bytes have been served raw since they were stored.

## Consequences

- Every row written from now on is the relay's own encoding of a verified event.
- Rows from before may hold verbatim client bytes — another key order, whitespace, keys no signature covers. Each passed `EventValidator` at admission, each has been served that way since it was written, and clients verify events themselves. An operator who wants them canonical exports with the old binary and re-imports.
- The relay's idea of an event's address is nostr-core's, for new and old rows alike, so replacement and deletion by coordinate act on the event a client means. A replaceable event carrying a `d` tag is filed under the empty identifier; an addressable event whose `d` tags disagree has no coordinate, is never replaced or coordinate-deleted, and the current `EventValidator` refuses such an event at admission, so no new one arrives.
- Upgrading a pre-0.2.0 database costs one indexed pass of SQL at first start, inside the migration transaction, and nothing at any later start. There is no operator step: export and re-import is a choice for byte-canonicality, never a requirement.
- Do not add another path that writes `raw_event` or `address_identifier`, such as a bulk import that inserts rows directly. Anything that stores events calls `store()` with an `Event`.
- Do not work an event's address out anywhere in the store except through `EventCoordinate::tryFromEvent()`. A second definition is the disagreement this record removes.
- Do not reintroduce a PHP pass that rewrites old rows' bytes. If byte-canonicality of an old database is ever wanted, the export and re-import path provides it.
- The comment on `raw_event` in migration 0001 describes the column as it was first written. It is left as applied; this record describes what the column holds now.
- `AddressIdentifierMigrationTest` pins every backfill case — the range boundaries, a Unicode identifier, agreeing, disagreeing, value-less and empty `d` tags, the untouched `raw_event`, replacement of a backfilled row through its `d` tag, and a fresh database — and `ImportEventUseCaseTest` pins that an imported line is stored in the relay's own encoding rather than as written.
